# 版本与分支管理

## 当前维护线

当前双入口简化版使用 `trace-only`，程序版本为 **10.2.0**。完整功能版保留在 `full-workflow`，两个分支独立维护。GitHub 的默认分支仍是历史 `main`，进入仓库或下载源码前应明确选择目标分支。

`10.0.x` 是之前只保留 Trace 分析的简化阶段。`10.1.0` 保留两个入口并统一版本标识，`10.2.0` 增加入口二的多模式并集选择。此前本分支的 `9.28.0` 是历史遗留标识，不代表代码停留在当时版本。完整分支及历史分支的版本标识不在此次修改范围内。

## 版本记录规则

- 根目录 `VERSION` 是唯一程序版本来源，格式为 `主版本.次版本.修订号`。命令行 `python plc_cli.py --version`、`workflow_manifest.json` 及两个入口的 `workflow_status.json` 均读取它。
- 不兼容的公共入口或交付格式变更增加主版本，兼容的新能力增加次版本，兼容修复增加修订号。纯文档修订由提交号标识。发布前同步 `VERSION`、README 与 CHANGELOG，合并为一个可回退提交。
- 程序版本、Git 提交号及 `pipeline_sha256` 分别标识发布、精确源码和执行规则。不同分支是不同维护线，版本号的数值不能替代提交关系或能力对照。
- 描述证据协议的 `schema` 是独立的接口版本；程序版本升级不自动改动 Trace v4 等协议编号。
- 发布时记录准确提交号及验证范围。需要发布标签时，简化版采用 `trace-v<版本>`，完整功能版采用 `full-v<版本>`，避免混淆；已有标签不移动。标签创建须在实际完成后报告。
- 更新程序后按指纹核验重新准备旧任务，保留原运行归档。不能修改旧产物中的版本字段来冒充新版本运行。

## 维护约定

长期维护 `trace-only`、`full-workflow` 两条线。历史分支保留点优先通过提交号或发布标签管理。清理前核对祖先关系、独立补丁和既有引用，不将历史实验线直接合并到当前分支。此次只记录用途，不删除、重命名分支，也不改默认分支。

## 离线同步

完整源码包解压到新目录，避免旧布局的脚本残留。Git 用户应用对应提交或补丁后，先查询版本，再执行回归与本工序核验。原始源码、Trace 和历史运行目录保持独立；新版本运行结果以实际状态文件和程序指纹为准。
